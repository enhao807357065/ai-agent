01 · 核心组件：谁负责什么？

主调用链 （从左到右，只有这一条路径可以执行副作用）

① Gateway Model

提出 Tool Call 或 Final。

不可信：参数、完成声明、自然语言结论。
→

② Pi Agent Loop

runAgentLoop / Continue

组织模型、工具回合、消息历史与 Hook。

不直接读写文件，也不决定业务完成。
→

③ Pi Tool Adapter

createPiRuntimeTools

仅转发 toolCallId、参数和 signal。

不访问文件，不重试，不改变状态。
→

④ ToolRuntime.execute()

schema → path → abort → handler

唯一副作用入口；返回受控结果。
Runtime 周围的可信状态与真实环境（这些不是另一条执行入口）

PlanStore

Plan DAG · Step · Evidence

VerificationOutcome：scope + testedDigest + latest result

completionIssues() 给出不能完成的具体原因。

Approval Gate

冻结精确源码写。

actionId + 参数 + targetDigest

文件变化后，旧批准自动失效。

Execution Environment

repositoryRoot · filesystem · npm child process

取消：SIGTERM → 等待 child close → 受控结果。
Checkpoint / Resume

保存 messages、Plan、actions、workspace digest。

Evidence Freshness

codeVersion + testedDigest + latest scope result。

Approval / Pause

waiting、paused、cancelled 各自保持语义。

Completion Contract

不信模型 Final；重新检查 Plan 与验证新鲜度。

Pi 编排层负责多轮交互和 Hook 时序；不越过 Runtime 直接执行。
Runtime 执行层负责所有受控副作用；Adapter 只负责传递 toolCallId、参数和 signal。
状态裁决层服务端记录 Evidence、验证范围与完成条件；模型不能直接写状态。

02 · 执行架构：一次 Run 如何收敛

一次任务的主路径 （上半部分向右执行；下半部分向下结算）

1 · CLI

解析 task、repository、state-dir、run-id。

构造受信启动配置。
→

2 · Assembly

创建 AgentContext、Runtime、Pi tools、Stop hooks。

只装配，不另起循环。
→

3 · Pi Loop

模型流 → Tool Call → Tool Result。

before / after / stop hooks。
→

4 · Runtime

校验、约束、执行 handler。

所有工具都经过 execute()。
工具成功或失败

成功：生成 Evidence draft。失败：返回 stable code；测试失败也记录真实验证结果。

afterToolCall

PlanStore 服务端盖章 step、call ID、codeVersion、testedDigest。

shouldStopAfterTurn

检查 unfinished steps、stale test、latest scope failure、budget 和审批。

下一步

完成 → completed；缺项 → FINAL_REJECTED；等待人审/取消/预算 → 对应状态。

关键分叉：模型输出“已完成”时，不会直接结束。Harness 先运行 Completion Contract：若测试证据过期、同范围最新测试失败、Plan 未完成或存在审批等待，都会返回具体缺项并继续/暂停，而不是伪造 completed。

取消

AbortSignal 从 CLI 进入 Pi、Runtime，再进入 npm 子进程；测试进程 close 后才结算取消。

恢复

先核对 workspace 与 action ledger。未知写入、未完整测试和现场不一致均 fail closed。

验证新鲜度

测试绑定实际受测 digest；同一 scope 的后续失败覆盖旧 pass，改代码后旧证据失效。
