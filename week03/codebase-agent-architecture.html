Week03 · Pi Native Codebase Agent

从“模型提出动作”到“受控 Runtime 执行”，并通过 Pi 原生 Loop 把结果与证据持续回写的代码库理解 Agent。

① 核心组件：职责、输入与不可替代边界

每个模块只做一件事；后面的装配层只注入它们，不复制其内部规则。

装配层

Agent Run

src/agent/codebase-agent-run.ts

单次 Run 的 Composition Root：在这里创建对象、连接依赖、观察事件；不实现工具、路径安全或停止算法。

它注入 / 组装
  • 可信 RunExecutionContext
  • ToolRuntime 与 AgentTool[]
  • RunStopCenter Hooks
  • 调用方提供的 model、streamFn
模型层

Gateway Model Runtime

src/model/gateway-models.ts

把“逻辑模型”注册进 Pi，并提供 Gateway 的流式入口；不在本地挑供应商或重试。

输出给装配层
  • model：Pi Loop 要使用的逻辑模型
  • stream(context, options)：流式请求入口
  • 环境变量解析的 Gateway endpoint / auth
框架循环

Pi runAgentLoop

@earendil-works/pi-agent-core

唯一的模型循环。负责消息转换、模型请求、Tool Call 调度、Tool Result 回写、Follow-up 继续。

从装配层接收
  • AgentContext：Prompt、消息、工具
  • AgentLoopConfig：模型、Hooks、转换策略
  • 取消信号和 streamFn
循环保护

RunStopCenter

src/agent/run-stop-center.ts

只根据 Hook 输入与自己的 Run 状态做停止决策；不读文件、不调用模型、不执行工具。

维护的 Run 事实
  • 动作指纹次数：第三次阻止
  • 当前轮次与最大轮数
  • 成功读取路径与成功产物路径
  • Final 不足时排队 FINAL_REJECTED
Pi 工具适配

AgentTool[] Adapter

src/tools/pi-runtime-tools.ts

协议转换层：Pi 工具接口 ↔ 应用 Runtime。它不拥有任何文件操作或路径权限规则。

做且只做
  • 声明严格 TypeBox 参数 Schema
  • 原样转发 toolCallId、参数、signal
  • 受控成功结果映射为 text + details
  • 受控失败抛出为 Pi 错误工具结果
唯一执行路径

ToolRuntime

src/runtime/tool-runtime.ts

所有实际工具执行的唯一入口：先治理不可信输入，再调用 handler；模型永远不直接接触底层文件系统对象。

强制执行的规则
  • TypeBox 二次参数校验、取消归一化
  • 仓库 / artifacts 根目录路径约束
  • 列表、搜索、读取、产物写入四种能力
  • 返回已治理 ControlledToolResult
关键分界：装配层负责“谁和谁连接”；Runtime 负责“是否可以执行”；Stop Center 负责“本 Run 是否该继续”。三者互不替代。

② 注入关系：为什么要把这些组件作为依赖传入？

注入不是为了“形式上的 DI”，而是为了让每一层可替换、可测试，并维持唯一执行路径。

调用方提供

model、streamFn、maxTurns、signal、可选 Runtime / 执行上下文 / 文本回调。

生产环境使用 Gateway 流；测试环境注入脚本化流，不走真实网络。

→

runCodebaseAgent()

唯一装配点：创建默认依赖，或使用注入的替代实现，然后调用一次 runAgentLoop。

model + streamFn
作用：决定“如何得到下一条 AssistantMessage”。抽象后，业务层不依赖具体 Gateway；脚本测试也能驱动真实 Pi Loop。
executionContext
作用：将“要分析哪里、产物写到哪里”作为可信服务端配置固定下来。模型只提交相对路径，不能改根目录。
runtime
作用：默认创建真实 Runtime；测试可注入同接口的替代 Runtime 来断言调用参数。但无论哪种，Adapter 都只走一个 execute() 入口。
maxTurns
作用：教学默认值保持安全上限；调用方可按任务预算覆盖，而停止逻辑仍集中在 Stop Center。
signal
作用：从外部取消传播到 Pi 流、Hook、Adapter 和 Runtime，避免引入第二套取消控制器。
onTextDelta
作用：把可见文本交给 CLI / UI；只转发 text_delta，不记录或展示模型隐藏 reasoning。

③ 核心运行流程

01 · 创建 Run

可信边界与依赖

创建或接收执行上下文、Runtime、Stop Center；由 Adapter 生成四个 Pi 工具。

输出：可执行的 AgentContext 与 Config。

02 · 模型请求

Pi 原生 Loop

只把 user / assistant / toolResult 转给模型。Gateway 返回 Assistant 文本或 Tool Call。

文本增量只进入 onTextDelta。

03 · 工具执行

Hook → Adapter → Runtime

Schema 校验后先检查重复动作；允许才转发到 Runtime；Runtime 治理后执行 handler。

任何文件读写都只能发生在 Runtime。

04 · 证据与停止

受控结果驱动状态

成功读取才记录源码路径，成功写入才记录产物路径；错误结果不产生证据。

在 turn_end 后完成校验，能读取本轮最新证据。

05 · 结束或续跑

Final / Follow-up

证据齐全则成功结束；证据不足时注入 FINAL_REJECTED，同一 Run 继续。

同一 Run：轮次、动作计数、证据均不重置。
